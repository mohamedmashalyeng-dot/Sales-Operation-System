# Canonical Architecture

Date: 2026-10-14

## Current Canonical Path

```text
frontend/src/
  -> built by Vite
frontend/out/
  -> served when present by
server/static-files.js
  -> called by
server.js

Browser
  -> /api/*
server.js
  -> server/routes/index.js
  -> direct DB route groups where available
  -> Storage.loadDb() workspace fallback where needed
  -> server domain modules and integrations
  -> PostgreSQL, MongoDB, or local JSON depending on DATABASE_URL
```

## Production Entrypoint

`server.js` is the production Node entrypoint. It creates the HTTP server, records API timings, delegates `/api/*` requests to `server/routes/index.js`, delegates static requests to `server/static-files.js`, and starts background jobs/schedulers after listening.

## Frontend Source Of Truth

The main frontend source is `frontend/`:

- `frontend/index.html`
- `frontend/src/main.tsx`
- `frontend/src/App.tsx`
- `frontend/src/components/`
- `frontend/src/pages/`
- `frontend/src/store/`

The build output is `frontend/out/`. It is ignored by git and should be generated by `npm run ui:build` or by the deployment pipeline.

## Legacy Frontend Path

The root legacy frontend remains intentionally available:

- `index.html`
- `app.js`
- `styles.css`
- `sw.js`
- `offline.html`
- `developer.css`

Evidence:

- `server/static-files.js` defaults to the Readdy build but falls back to legacy static files if `frontend/out/index.html` is unavailable.
- `scripts/start-legacy-ui.js` sets `KBC_UI=legacy`.
- `scripts/security-static-smoke-test.js` sets `KBC_UI=legacy`.
- `sw.js` caches `app.js` and `styles.css`.

This path should not be deleted until fallback behavior and smoke tests are replaced.

## API Routing Layer

`server/routes/index.js` is the routing boundary. It applies security headers, parses request bodies, gates authenticated routes by session cookie, then tries route groups in this order:

1. Open routes: health, login/password callbacks.
2. Direct routes: database-backed route handlers that avoid loading the full workspace.
3. Public workspace routes.
4. Authenticated workspace fallback routes after `Storage.loadDb()`.

This layered routing is an active performance design and should not be collapsed without route-by-route verification.

## Business Logic Layer

The current business logic lives in existing domain modules under `server/`, including:

- `server/leads.js`
- `server/applications.js`
- `server/emails.js`
- `server/events.js`
- `server/tasks.js`
- `server/dashboard.js`
- `server/monitoring.js`
- `server/analytics.js`
- `server/automations.js`
- `server/integration-centre.js`

`server/routes/*` should stay close to HTTP concerns, but many route files still call domain modules and contain fallback logic. Future cleanup should extract only small, proven duplicate blocks.

## Database Layer

`server/storage.js` is the storage adapter boundary.

Production should use PostgreSQL/Neon via `DATABASE_URL` or `POSTGRES_URL`. The code still supports MongoDB and local JSON:

- PostgreSQL: production target and normalized tables.
- MongoDB: documented runtime branch, not proven dead.
- Local JSON: local/dev/test fallback, not production source of truth.

Production should fail clearly if a real production environment lacks a production database URL; that hardening should be done as a separate behavior change with deployment review.

## Background And Sync Layer

Background scheduling starts from `server.js` via `Jobs.startAutoSync()` and monitoring schedulers. Integration sync state and workers live under:

- `server/jobs.js`
- `server/integrations/gmail.js`
- `server/integrations/zoom.js`
- `server/integrations/zoho.js`
- `server/integrations/eventbrite.js`
- related scripts in `scripts/`

No sync behavior was changed in this cleanup pass.

## Authentication And Authorization

Authentication and authorization are active modules:

- `server/auth.js`
- `server/authorization.js`
- `server/routes/account.js`

Several route handlers call `Authorization.requireRecord(...)` before record-level operations. Any future route move must preserve those checks.

## NestJS Compatibility Path

`src/main.ts` is a Nest wrapper around the legacy server modules. It sets `NEST_COMPAT_MODE=true`, uses `legacy.handleApi(req, res)` for API routes, and uses `legacy.serveStatic(req, res)` for static routes.

Because `package.json` includes `start:dev`, `build`, Nest packages, and `src/` modules, NestJS is not proven dead.

## Service Worker Path

`sw.js` belongs to the legacy frontend path. It caches shell assets only, skips API requests, and unregisters in local dev via `app.js` behavior. The Vite frontend does not currently register a separate service worker in source.

## Deployment Summary

Expected production deployment:

1. Install dependencies.
2. Build frontend with `npm run ui:build` unless deployment does this automatically.
3. Start `server.js` with `npm start`.
4. Serve `frontend/out/` through `server/static-files.js`.
5. Use PostgreSQL/Neon for production storage.

If `frontend/out/` is absent, the app intentionally falls back to the legacy UI.
